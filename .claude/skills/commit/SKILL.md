# コミット作成

変更内容を確認し、適切なコミットメッセージでコミットを作成します。

## 鉄則

```
git add . は使わない。ファイルを個別に指定する
```

## 依頼内容

$ARGUMENTS

## 実行手順

### 1. 現状確認（並列実行）
- `git status` で変更ファイルを確認
- `git diff` でステージ前の差分を確認
- `git diff --cached` でステージ済みの差分を確認
- `git log --oneline -10` で直近のコミットスタイルを確認

### 2. コミットメッセージ作成
- 直近のコミットメッセージのスタイルに合わせる
- 変更の種類に応じたプレフィックスを使う：
  - `feat:` 新機能
  - `fix:` バグ修正
  - `refactor:` リファクタリング
  - `test:` テスト追加/修正
  - `docs:` ドキュメント
  - `chore:` その他（設定、依存関係など）
- 簡潔で「なぜ」がわかるメッセージにする

### 3. コミット実行
- 対象ファイルを `git add` する（`git add .` は使わない）
- コミットメッセージはHEREDOCで渡す
- `.env` やクレデンシャルファイルは絶対にコミットしない

### 4. 確認
- `git status` でコミット後の状態を確認

## TDDサイクルとの関係（粒度）

- 粒度の基準は「サイクル数」ではなく「責務」。**1サイクル=1責務が成立していれば1コミット**にする
- 成立していなければ、責務ごとに `git add <ファイル指定>` で分割する
- **REFACTOR まで終えてからコミット**する（GREEN の途中では刻まない）
- ただし REFACTOR が大きい／性質が違う整理のときは、実装と分けて2コミットにする
  - 例: `feat: 部屋の公開ピーク表示を追加`（RED+GREEN） / `refactor: ピーク判定を RoomPolicy に抽出`（REFACTOR）
- **RED 単独ではコミットしない**（わざと落ちるコミットは `git bisect` を濁す）。GREEN まで進めてまとめる
- GREEN が長引いて不安なら、一時コミットに頼らず **Task を小さく割る**サイン
- 判断のコツ: メッセージが「1行で説明できるか」。"and" が入るなら分割

## ルール

- `git add .` や `git add -A` は使わない。ファイルを個別に指定する
- `--no-verify` は使わない
- `--amend` はユーザーが明示的に指示した場合のみ
- 機密ファイルをコミットしない
